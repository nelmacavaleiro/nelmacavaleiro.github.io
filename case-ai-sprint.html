AI deployment sprint: from discovery to solution design for a UK manufacturer

From discovery and analysis to designing and building a working tool that removes repetitive design work, with people kept in control at every stage.

Role
Team Lead
Period
October to November 2026
Focus
Business analysis, solution design and build
Status
In progress

Context

An eight-week AI Deployment Sprint delivered by Manchester Digital with Manchester Metropolitan University. I lead a team working with a UK manufacturer of leisure safety products.

The problem

Preparing bespoke products for automated cutting involves repetitive manual design work across several software tools that are not connected to one another, which limits the capacity of the person who does it.

My role

As Team Lead, I am responsible for planning, coordination, documentation and client communication. In practice, I have also led much of the business and technical analysis and the solution design.

Discovery and business analysis

  • Agreed the problem statement with the client and mapped the order-to-manufacture process in BPMN, reviewed and approved by the person who does the work.
  • Timed the current process: a standard design took 25 minutes, of which the manufacturing drawing alone took 72%. This showed where the real time cost was, which was not where it had first been assumed.
  • Wrote the business analysis: stakeholders and pain points, baseline measures, root cause analysis (fishbone and 5 Whys), constraints, user stories with acceptance criteria, and the business case.
  • Captured a traceability requirement from operations and built it into the solution criteria.

Technical analysis with Python

  • Analysed 130 design and production files using Python in VS Code, with AI-assisted development, running everything locally and read-only. I used ezdxf to read and measure the cutting files, pypdf to extract details from drawings and orders, and zipfile to open the design files and extract the formulas behind the parametric model.
  • Compared raw design exports with finished production files for a real order, identifying exactly which steps were manual, and found and resolved a 30 mm dimensional discrepancy.
  • Derived the cutting machine's file requirements from its configuration and tested sample files against them.

Rules discovery and validation

From the analysis, I extracted the design, manufacturing, machine and drawing rules, labelled as observed until confirmed, then validated them with the client: over 40 rules in a documented register. An automated check showed the rules reproduced the finished cutting files, passing 11 of 11 and 14 of 15 checks. Where sources disagreed, I raised the inconsistencies and resolved them with the client.

Solution design

  • Wrote the solution analysis: capabilities, functional and non-functional requirements with MoSCoW priorities, guardrails, a review of existing software, an options evaluation, feasibility tests and a recommendation.
  • Designed a rules-based order-to-production tool that reads the sales order, applies the documented rules and produces the cutting file and manufacturing drawing, with human approval at each stage. AI is used to help build the tool, not inside it, so production decisions stay predictable and checkable.
  • Designed it around two needs: saving the designer's time, and traceability for operations.

Building the tool

I designed and built a Python and Flask tool that turns a sales order into a cutting file (DXF) and a manufacturing drawing, with the designer approving every stage. I wrote the specification first, then delivered the work as 18 small user stories, directing Claude Code as the implementation agent against the specification, written coding rules and acceptance tests for every story. I approved each plan before any code was written and reviewed every change before it was merged.

  • A layered architecture, with automatic checks that enforce which parts of the code may call which.
  • Automated quality gates on every commit: ruff, mypy (strict), import-linter and pytest, with a separate branch for each story.
  • An order reader that verifies every line and refuses anything it cannot check, so errors are caught before anything is generated.
  • No AI inside the tool and no external services: the rules are applied in plain code, so the same order always gives the same result, and client data stays within the client's environment.

Testing and validation

  • Generated cutting files were compared automatically against the client's approved reference files.
  • Cutting files loaded on the client's cutting machine software with correct dimensions.
  • Ambiguous rules and labelling conventions were resolved directly with the designer before being built, rather than guessed.
  • A user trial with the client's team has been set up to gather feedback on the working tool.

Handover

I produced install, user and maintenance guides, and demonstrated the working solution live to the client and to the programme team, including the structured approach used to build it.

Outcome so far

The tool works end to end for standard products, from order to cutting file and drawing. Some tests are still to come, such as nesting on the cutting machine, and the time and cost savings have not yet been measured, so they remain targets. Final outcomes will be shared here once the client has approved what can be published.
